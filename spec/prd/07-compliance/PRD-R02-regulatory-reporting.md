## 1. Problem Statement

Insurers owe a steady stream of reports: statistical data to rating/statistical organizations, financial statement schedules (e.g., loss development data), market-conduct data calls, complaint and claim-timeliness reports, fraud-bureau referrals, and — for MGAs and delegated-authority programs — premium and claims bordereaux to carriers and capacity providers. These are usually assembled by hand from inconsistent extracts, with no ability to reproduce what was filed. The platform needs report definitions over a bitemporal regulatory data mart with lineage, reproducible point-in-time runs, review/sign-off, and submission tracking.

## 2. Goals
1. **On-time filing**: 100% of scheduled reports produced and submitted by due date.
2. **Reproducibility**: any filed report can be regenerated byte-equivalent from stored definition version + data as known at filing time.
3. **Lineage**: 100% of reported figures traceable to source records.
4. **Effort**: −60% manual effort per recurring report vs. baseline.

## 3. Non-Goals
- **Actuarial reserving and capital models** (consume data; not computed here).
- **Statutory financial statement preparation** end-to-end (R02 supplies schedules data; finance systems produce statements).
- **Tax filings.**

## 4. Personas & User Stories
- As a **regulatory reporting analyst**, I want to run a market-conduct data call extract for a period, review exceptions, and submit with sign-off.
- As a **compliance officer**, I want claim-timeliness and complaint reports by jurisdiction from C02 deadline data.
- As an **MGA operations lead**, I want monthly premium and claims bordereaux per capacity provider in their required format.
- As an **actuary**, I want loss development triangles data (paid/incurred by accident period and development age) from ledger-backed claim financials.
- As an **auditor**, I want to see exactly which data and definition version produced a filed report.
- *Edge:* late-arriving correction after filing → amended report workflow with diff.

## 5. Domain Model & Invariants
| Entity | Notes |
|---|---|
| **Report Definition** | regulator/recipient, format (file spec), schedule, query/semantic model refs, validations, version, effective period |
| **Report Run** | definition version, period, `asOf` and `knownAt` parameters, data snapshot ref, output artifacts (F06), validation results, state |
| **Submission** | run, recipient, channel, submitted-at, acknowledgement, amendments |

**Run states**: `SCHEDULED → RUNNING → VALIDATION_FAILED | READY_FOR_REVIEW → APPROVED → SUBMITTED → ACKNOWLEDGED | REJECTED`; `SUBMITTED → AMENDED (new run)`.

**Invariants**
- INV-R02-1: Runs use bitemporal data as known at `knownAt`; rerunning with the same parameters reproduces output.
- INV-R02-2: Submitted outputs are immutable documents with hashes; amendments are new runs linked to the original.
- INV-R02-3: Approval requires a principal ≠ preparer (SoD).

## 6. Requirements
### P0
- **R02-P0-01** Regulatory data mart (in A01 platform) with bitemporal facts for policies, premiums, claims, payments, recoveries, deadlines, complaints.
- **R02-P0-02** Report definitions as versioned configuration with validations.
- **R02-P0-03** Run orchestration with `asOf`/`knownAt`, exception reports, review & sign-off, submission tracking, archive to F06.
- **R02-P0-04** Launch report pack: claim timeliness & deadline compliance, complaint log, statistical data extract (per launch jurisdiction stat plan), loss data triangles extract, premium/claims bordereaux (for MGA tenants), fraud referral log.
- **R02-P0-05** Lineage from report cell → aggregation → source records.
### P1
- **R02-P1-01** Market-conduct data call templates and ad-hoc extract builder.
- **R02-P1-02** Direct submission adapters where regulators/recipients offer APIs/portals (S02).
- **R02-P1-03** Reinsurance bordereaux.
### P2
- **R02-P2-01** Solvency-regime quantitative reporting data feeds (non-US tenants).
- **R02-P2-02** Regulator self-service portal (with F02-P2-02).
